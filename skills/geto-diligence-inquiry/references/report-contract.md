# 询盘背调 Markdown 报告合同

## 1. 报告定位

`report.md` 是面向销售和管理人员审阅的第一交付。事实以 `company.json` 和内嵌 Evidence 为准；报告把完整公司画像与当前询盘判断综合成自然中文，不逐项转写 JSON，也不汇报工具操作过程。

研究可以广泛深入，正式报告必须务实易读。正文只保留会改变公司真假、联系人权限、项目与采购窗口、产品方案、报价/签约/付款/授信、客户价值或下一步动作的信息；其余进入结构化档案、专题材料、查询记录或 `Sources/sources.md`。

## 2. 核心问题

报告必须回答，但不规定章节数量：

- 总体判断和当前建议是什么；
- 询盘提出了什么，需求成熟到什么程度；
- 公司从历史至当前的身份、能力和经营状况如何；
- 联系人是否任职、是否有权限、还有哪些可用联系方式；
- 最可能对应什么项目或采购场景，采购窗口是否存在；
- GETO 产品和技术是否适配，还缺哪些输入；
- 现在能否报价、签约、授信或承诺交期；
- 公司是否值得长期投入；
- 销售下一步问什么、索取什么、发送什么、暂时不承诺什么。

## 3. 动态章节

固定核心问题，不固定模板，也不固定章节数量。简单询盘可以合并章节；复杂询盘按实质发现增加专题。章节数量、篇幅和表格数量都不是研究深度指标。

可能的动态专题包括：

- 股权、集团、JV、SPV、历史主体或品牌迁移；
- 域名迁移、旧站、同名污染或冒名；
- 关键项目、采购链、供应链或决策网络；
- 制造、租赁、安装、经销、跨境履约或海关；
- 财务主体、付款能力、诉讼监管、制裁或重大负面事件；
- 特定产品系统、工程方案、法规或技术标准；
- 项目时序冲突、历史业绩归属、竞争系统或供应商锁定；
- 其他会显著改变业务理解的发现。

专题进入正文前至少满足一项：改变核心结论；改变项目、产品或交易动作；解释重大冲突；形成高价值机会或重大风险；属于用户明确关注内容。

## 4. 阅读顺序

章节名称和数量可以变化，阅读逻辑保持：

```text
结论与建议
→ 询盘和目标对象
→ 最重要的公司事实与专题发现
→ 对项目、产品、采购和交易的影响
→ 客户价值与风险
→ 下一步动作
→ 研究限制与来源
```

第一页优先呈现总体判断、当前动作、3–5 条关键依据、3–5 条关键限制和销售下一步。

## 5. 公司轴与询盘轴

公司轴必须覆盖从历史至当前的主体、业务、项目、关系、人员、财务、海关、合规、新闻社媒和长期价值。询盘轴必须覆盖需求、联系人、项目匹配、技术输入、采购链、签约付款和准备度。

两条轴合并叙述，不重复事实。公司资料只有在影响当前询盘、长期价值、合作方向、风险或销售策略时进入正文；其他完整信息保留在 ResearchBundle。

## 6. 项目内容

- 先给项目池总体判断；
- 用“公司项目池”或同义标题提供紧凑总表，逐项覆盖 `company.json.projects[]` 的全部项目；
- 总表至少包含项目名、地点、类型/规模、历史/当前/规划状态、公司角色、与本询盘或 GETO 的关系；
- 项目正式名可以保留原语，必要时给出中文解释；不得因汉化而删掉项目身份；
- 多个具名项目不得在 `projects[]` 或报告中压缩成一个“历史项目池”占位；
- 正文重点解释最可能与询盘相关、当前性最强或最能改变结论的项目，通常 1–3 个，但不设固定数量；
- 每个重点项目回答项目是否真实、目标公司是否参与、真实角色是什么、对本次询盘是否仍有采购意义；
- 历史案例支持能力，不直接等于当前需求；
- 其余项目保留在总表，详细字段和查询记录可进入专题材料或内部索引；
- 不因为项目多就逐个建立独立章节。

## 7. 联系人与触达

正文围绕“怎么联系、是否任职、有没有权限”说明：姓名、职位、公司/部门/具名联系方式、任职证据、技术/采购/签约/付款权限和销售使用建议。

数据服务请求过程、匿名记录、技术错误和请求编号不进入正文；只说明是否找到可采纳增量、有什么限制。邮箱可投递不证明任职和授权。

## 8. 风险与评分

核心风险必须可行动：说明业务影响、缓释动作和解除条件。泛化风险、重复缺口和无缓释动作的理论风险不进入核心表。

询盘准备度回答当前能否报价和推进；长期客户价值回答是否值得持续投入。评分服务于判断，不主导报告。缺少同类样本时可展示观察和解释，但用“同类样本不足，暂不出具最终等级”，不展示内部状态码。

## 9. 极致汉化

正式报告不得直接展示大段外语、snake_case、JSON 字段、API 状态、机器状态、请求编号、调试日志或以下内部术语：

- `pending_cohort_baseline`、`nurture_or_verify`、`not_requested`；
- `diligence_with_identity_gaps`、`blocked_no_research_anchor`；
- `Provider`、`queryBoundary`、`hard block`；
- `unverified_signing_and_payer`、`ready_for_quotation`；
- 其他机器枚举和错误状态。

改用自然中文：

| 内部概念 | 正式表达 |
| --- | --- |
| Provider | 第三方数据服务，或直接写服务名称 |
| no_result | 在已检查范围内未发现匹配记录 |
| buyer / payer | 采购方 / 付款方 |
| actual user | 实际使用方 |
| technical approver | 技术选型或审批人 |
| signing entity | 合同签约主体 |
| nurture_or_verify | 继续培育并补充核实 |
| pending_cohort_baseline | 同类样本不足，暂不出具最终等级 |
| hard block | 关键交易阻断 |

法定名称、项目正式名、品牌和产品系统可以保留原语；首次出现的英文角色或缩写给出中文解释。

## 10. 务实易读

- 结论在前，依据和限制在后；
- 一句话表达一个主要判断，一段通常 2–4 句；
- 每个重要事实说明“对本次业务意味着什么”；
- 表格只用于询盘字段、项目对比、联系方式、风险、评分和待补资料等明显更清楚的关系；
- 不用篇幅证明深度，不重复同一事实；
- 下一步必须具体到问题、资料、发送内容、报价前提、暂不承诺事项和复查触发条件；
- 必要时提供可直接发送给客户的沟通话术。

## 11. 证据和不确定性

报告区分事实底座、关键信号、AI 推理、AI 结论、不确定性和继续研究方向。弱信号可用于假设和下一跳，不得包装成法定主体、客户关系、采购方、付款方或授权事实。

主体、域名或人员冲突的完整候选矩阵留在内部审计。只有冲突实质影响真假或交易判断时，才在相关专题用自然中文说明最可能解释、替代解释、证据和影响。

“未发现”必须写明已检查范围，不能写成“不存在”。项目金额不能写成目标公司收入；集团财务不能写成目标法人单体财务。

## 12. Markdown Review 门禁

生成 `Sources/sources.md` 并运行工作空间和报告质量检查后，先向用户交付 `report.md`，请求审阅内容、章节取舍、评分、结论和语气。

用户提出修改时，先同步更新 `company.json`、Evidence、Sources 和 `report.md`。未获得明确确认时，不默认生成 DOCX/PDF。需要发布文件时读取 [publication-contract.md](publication-contract.md)。

## 13. 内容验收

进入用户 Review 前确认：

- 公司轴和询盘轴均有结果或明确边界；
- 公司项目池已尽量枚举，`projects[]` 每个项目均在正文总表出现；没有具名项目时已说明查询范围和边界；
- 核心业务问题均得到回答；
- 动态专题由重要发现驱动，不是为了凑章节；
- 读者在第一页知道是否继续、怎么继续和暂时不能做什么；
- 正文无内部术语和难懂机器码；
- 删除任一章节后若不影响业务判断，该章节已被移出正文；
- 非研究人员无需查看 JSON 即可理解结论；
- 报告与 `company.json`、Evidence 和 Sources 一致。
