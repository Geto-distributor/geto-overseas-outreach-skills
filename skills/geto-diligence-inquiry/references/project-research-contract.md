# 询盘项目研究合同

## 1. 研究命题

项目研究分别证明，不能合并推断：

1. 项目真实存在；
2. 目标公司实际参与；
3. 目标公司的合同角色和范围；
4. 目标公司是否影响技术选型、采购、签约或付款；
5. 项目是否与本次询盘相关；
6. 当前是否仍有 GETO 产品采购窗口。

项目总投资、主合同金额或开发总值不等于目标公司收入。公司官网项目卡片只证明企业公开声称参与，必须继续核验角色和时态。

## 2. 项目池广度扫描

尽量建立公司从历史至当前的项目池：

1. 枚举官网 Projects、Portfolio、Case Studies、News、sitemap、图片标题和 PDF 项目表，记录总量、分页和时间边界；
2. 用法定名、品牌、域名、项目别名和城市组合检索政府规划、许可、招标、授标、合同、审计和法院材料；
3. 沿业主、开发商、总包、JV、顾问、分包商和供应商官网反查；
4. 用项目人员履历、行业媒体、专业数据库、协会、展会和公开社媒补充合同包、阶段和时间线；
5. 对询盘明确项目单独检索项目名、地址、业主、总包、顾问、采购编号和结构/工法；
6. 询盘没有项目名时，围绕城市、产品、数量、交付期和公司当前项目建立匹配假设；
7. 把查询写入 `researchQueries[]`，区分已找到、已查无结果、部分覆盖、失败和未查询。

项目池区分历史、当前、未来和未知，不用弱来源凑数量，不把别名或多个网页重复计数。

## 3. 高价值项目和关系路径

完成项目池扫描后，选择最可能增加商业理解或改变询盘判断的项目或关系继续深挖。通常 1–3 个项目进入正式报告重点分析，但不设固定数量；复杂询盘可增加，简单询盘可减少。

优先：

- 询盘明确点名或高度匹配的项目；
- 当前性强、产品相关度高、规模显著或仍有采购窗口的项目；
- 能闭合 owner、总包、分包、buyer、payer、actual user 或 technical approver 的项目；
- 反复出现的客户、供应商、系统或参与方；
- 可能改变主体、角色、产品适配、长期价值或风险的项目；
- 能找到具名项目人员、采购入口或后续包件的项目。

记录选择理由。没有进入重点深挖的项目，用简表、索引或内部专题保留，不平均用力。

## 4. 深挖字段

每个重点项目尽量核查：

- 名称、别名、地点、类型、规模、层数、面积、单位数；
- 业主、开发商、总包、JV、分包、顾问、设计、监理和供应商；
- 状态、采购阶段、开竣工或审批时间线；
- 公开金额及其口径；
- 目标公司的角色、合同范围、角色验证状态；
- buyer、payer、actual user、technical approver、signing entity；
- 结构体系、模板系统、产品、数量和供应商；
- 采购、租赁、甲供、安装和现场服务边界；
- 当前剩余包件、采购窗口和 GETO 切入点；
- 与本次询盘的匹配、支持、反证、冲突和缺口。

## 5. 时间和归属

- 历史案例支持能力，不直接计入当前需求；
- 法人成立前项目不能自动归入该法人业绩；
- 旧项目页面的“进行中”标签必须按检索日期复核；
- 项目真实不等于目标公司参与；
- 参与不等于采购、付款或签约权限；
- 项目仍施工不等于模板采购窗口仍开放。

## 6. 报告表达

正式报告先给项目池总体判断，再重点解释会改变询盘和公司价值判断的项目。每个重点项目用自然中文回答：

- 项目是真是假；
- 公司有没有参与；
- 公司是什么角色；
- 与本次询盘有什么关系；
- 现在还有没有采购意义。

完整查询覆盖、未选择项目和技术字段留在内部项目索引或 ResearchBundle。项目少时说明查询边界，不强制生成独立“项目检索覆盖”正文章节。
